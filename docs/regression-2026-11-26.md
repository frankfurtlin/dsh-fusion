## 3. 问题清单

### P1（高）主机状态长期显示「登录…」，与实际连接矛盾

- **现象**：抽屉底部主机 chip、远程主机页「正在使用『dsh』」、网页登录主机行，三处都显示
  「● 登录…」；同时抽屉能列出 189 个会话、会话可打开、回复可流式输出（图 04/08）。
  连续观察 20 分钟仍未变化。
- **代码位置**：`app/lib/ui/remote/host_status.dart:21-24`
  `HostLinkPhase.connecting` 且 `step == login` 时显示 `『登录…』`；
  说明**UI 读到的 link 相位停在 connecting**，而真正承载流量的是另一条 link 实例。
- **疑似成因**：
  1. `hostLinkProvider` 为 `Provider.autoDispose.family`，页面重建会新建一条 link，
     每条 link `open()` 都会**重新走一次网关登录**（`GatewayLogin`），旧的那条仍在承载流量；
  2. `GatewayLogin._csrf/_submit` 读取响应体（`transform(...).join()`）**没有超时**，
     只有连接与首包有 `.timeout()`；网关偶发挂住时该 future 永不完成 → 相位停在 login；
  3. 成功后也没有把 mux 的 ready 状态回灌到 status。
- **修复建议**：
  - 同一主机全 App 只保留一条 link（用 `ref.keepAlive` 或状态层缓存），页面只读不改；
  - `GatewayLogin` 每次请求整体加 `Future.timeout`（含 body 读取），超时映射为 `unreachable`；
  - 连接成功后以 mux `ready` 事件作为唯一真值覆盖相位；
  - 文案上，connecting 超过 15 s 应显示「正在重试」而不是停在某个步骤名。

### P2（中）本机引擎：`manifest: runtime/manifest.json` 缺失

- 现象：设置 → 主机 → 本机引擎「出错了」；诊断页错误原文 `manifest: runtime/manifest.json`，
  内置版本/已安装版本/DSH/Node.js 均为 `–`，当前运行方式「未运行」。
- 影响：手机本地引擎不可用（用户当前用网页登录主机，主链路不受影响）。
- 方向：核查 APK 里 runtime 资产的打包与首次解压（`允许访问文件` 未开启也可能影响落盘），
  并在诊断页把「缺失清单文件」翻译成一句可操作的话。

### P3（中）会话列表与打开的性能抖动

见第 4 节。189 行会话，`session_list` 16 次采样里 7 次 > 6 s；`session_open` 最慢 8.9 s
（`records=449`、`building=true`）。

### P4（低）失败提示是英文技术串

「请求失败，正在重试（1/5）」下面直接给 `TRANSPORT` / `Connection error.`，
对普通用户无意义；建议中文说明 + 「点开查看」保留原文。

### P5（低）无障碍标签过长

工具卡片（`运行`/`思考`）的 contentDescription 是**整段命令与输出**，
其中一条包含数千字符的 heredoc（本次 UI tree 单节点即 >8 KB）。
读屏会一字不漏念完。建议 desc 截断为「运行命令，点开查看详情」。

### P6（低）系统权限与手机桥的无障碍状态不一致

系统权限页「打开无障碍 未开启」，但手机桥 a11y 能力实际可用（本次全程靠它操作）。
两个不同的无障碍服务没有在同一处解释清楚，用户会困惑。

### P7（提示）未登录 DeepSeek 账号、API Key 未设置

概览卡与用量面板都提示；用量面板的「DeepSeek 余额」因此不可用。属预期，非缺陷。

### 分析

1. **启动不是瓶颈**：boot 77 ms、首屏 337 ms，接近原生体验。
2. **会话列表是瓶颈**：189 行 × 每次全量拉取，16 次采样中位数约 3.8 s，最慢 8.3 s；
   而 `session_list_cached` 只用 0 ms 就铺出 93 行 —— 说明**缓存只覆盖首屏**，
   剩下 96 行必须等网络。用户感受就是「列表先出来一部分，然后卡住」。
   > **更正（2026-11-26 18:00，P3 收尾时核实）**：这一条推断是错的。那台 Host
   > 当时的 189 行是 **93 个真人会话 + 96 个子会话**（`origin == subagent`）。
   > 子会话在抽屉里从来不显示（`sessions_state` 的 `_visible` 与快照的 `save`
   > 都滤掉 `isSubagent`），所以 93 行就是抽屉能显示的全部，不是首屏。
   > 核实：扫 `/root/.dsh/sessions` 的 201 份会话头 + `workspace.json`，按
   > `createdAt` 取 11:44:09 之前的 = 189 份（96 子会话 + 93 真人），和
   > `rows=189` 一模一样；快照文件实测约 19 KB（93 行 × ~200 B），离
   > 512 KB / 400 行的上限很远 —— 没有掉行，也不是旧文件。现在
   > `session_list` 那行会带 `top=`（非子会话行数）、`same/changed/added`
   > （和上一次列表的差），`session_list_cached` 会带 `total=`（写快照时的
   > 全量行数）和 `ageS`（快照多旧），下次不用再数一遍。
3. **会话打开**：1.3–8.9 s，`records` 352–593，`building=true`（生成中）时最慢（8.9 s）——
   打开一个正在生成的会话要等全量记录。
4. 抖动幅度大（269 ms ↔ 8283 ms）说明瓶颈在**网络往返 + 全量负载**，
   而不是渲染（渲染在 269 ms 那次已包含）。

### 优化建议（按性价比排序）

1. **增量/分页**：`session_list` 走游标（按 `updatedAt`），首屏 30 条 + 滚动加载；
   或服务端只返回变化（`since` 参数）。
   > **核实（2026-11-26）**：这个 Host 现在做不到。`session/list` 的
   > `SessionListRequest` 只有一个 `cursor?: string`，服务端 handler 第一行就是
   > `async list(_request, signal)`（参数名带下划线、注释写 "reserved empty list
   > request"），返回 `{items}` 里没有下一页游标 / `hasMore`。要真分页得先改
   > Host，客户端别自造。
2. **缓存写全量**：把 93 行快照扩到全部 189 行（体积仍很小），冷启动 0 ms 铺满，
   网络刷新后台进行并只做 diff 合并。
   > **核实（2026-11-26）**：快照本来就是「抽屉能显示的全部行」= 93 行（子会话
   > 不落盘），不需要扩容；本次（P3 收尾，未发版）把刷新改成按行 diff 合并
   > （没变的行留用原实例、内容没变就不重发列表），并给快照写入加了顺序与
   > 超限截断的兜底。
3. **去重刷新**：本次 16 次 `session_list` 大多来自抽屉开合/切主机/回到前台；
   加 30 s 节流 + 复用 mux 推送的增量事件（`SessionStatusEvent` 已有处理）。
4. **会话打开分页**：先取最近 100 条渲染，向上滚动再取更早；
   `building=true` 时不要等全量记录再显示。
5. **网关链路**：确认 `/api/*` 走 gzip + keep-alive，并把多次小 RPC 合并为一次批量请求。
